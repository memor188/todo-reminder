## 一、产品目标和使用场景

**目标一句话**：一个安卓手机上的日程待办 App，核心是"到规定时间提醒我要做什么"。

**原动力**：用户现有的课程表 App 有日程功能，但**没有 AI 对话录入**。AI 对话是本项目的差异化核心，不是锦上添花。

**真实使用场景**：

1. **考试提醒**：课堂上老师说"周五 17 点 E 栋 104 考试"——打开 App，把这个句子丢给 AI，草稿卡片出现"事件型 / 2026-11-27 17:00 / E栋104 / 考试"，核对后入库，到点通知。
2. **学期课程**：开学把课表文本粘给 AI 解析成一学期的课程（V3），平时不需要手填二三十门课；课程按周期规则重复，改一次地点 = 改整学期。
3. **临时任务**："取快递""交作业"——当天做完打勾消失，不需要精确时刻，提醒策略与考试不同（当天提一次即可）。

**非目标**：不做多人协作、不做账号系统、V1 不做云同步、不做后端。自用 + 发 APK 给朋友各用各的。

## 二、整体页面框架和导航结构

底部三个 tab：**`日程` / `课表` / `我的`**。

```
App
├─ 日程 tab（V1 主视图）
│  ├─ 首页：日程列表（见第三节）
│  ├─ 手动录入页（点 + 进入）
│  └─ AI 对话页（点 + 进入，V2 开放）
├─ 课表 tab（V2 开放，V1 显示占位提示）
│  └─ 周网格视图：7 列 × 时间轴
└─ 我的 tab
   ├─ AI 供应商配置（baseURL / apiKey / model）
   ├─ 提醒偏好（V2 起）
   └─ 数据备份 / 恢复（见第七节）
```

**版本差异**：

| tab | V0 | V1 | V2 |
|---|---|---|---|
| 日程 | 单页探针（无 tab） | ✅ 完整列表 | ✅ |
| 课表 | — | 占位提示"V2 开放" | ✅ 周网格 |
| 我的 | — | ✅ AI 配置 + 备份恢复 | ✅ + 提醒偏好 |

> 导航从 V1 起就是三 tab 结构，V2 只是把占位换成实际内容，不改导航骨架。

## 三、首页内容结构

**V1 日程列表页**：

- **顶部**：日期标题（如"11月21日 周六"）+ 7 天日历条；有课的日子标圆点。
- **主体**：按日期分组的时间线，三类条目混排：
  - **课程**：灰蓝底 + 「课」标签，显示时间段（08:00–09:40）与地点；
  - **事件**：左侧强色条（红/橙），显示时刻 + 地点，到点必须在那；
  - **任务**：虚线圈 + 圆形勾选框，时刻可空（只显示日期）。
- **悬浮按钮** `+`：弹出两个入口——「手动填写」「问 AI」（V1 中 AI 入口点击后提示"先去设置填 key"或"V2 开放"，按实现进度定）。
- **空状态**：当天无条目时显示引导文案，不做空白页。

**排序规则**：课程先按周期规则展开成具体日期，再与事件、任务按时间排序；任务无时刻时排在当天末尾。

## 五、每个模块第一版必要的数据和操作

### 5.1 日程列表模块
- **必要数据**：日期分组、条目类型标识、事项标题、时间（课程用时间段 / 事件用时刻 / 任务日期可空）、地点、完成状态。
- **必要操作**：滚动浏览；切换 7 天日历条选日期；任务点勾选框 → 消失；点条目查看详情（V1 只读，编辑推 V2）。

### 5.2 手动录入模块
- **必要数据**：事项（必填）、类型（课程/事件/任务，必选）、日期、时刻（任务可空）、地点（可空）、备注（可空）。
- **必要操作**：选类型 → 填字段 → 保存 → 返回列表看到新条目；能取消不保存。

### 5.3 本地提醒模块
- **必要数据**：提醒时间（绝对时间）、事项标题、通知渠道 id。
- **必要操作**：保存条目时注册提醒；到点通知栏出现一条；用户点击通知能回到 App。
- **V1 边界**：只做"到点"软提醒；无提前量、无贪睡、不管后台被杀。

### 5.4 我的 / 设置模块
- **必要数据**：baseURL、apiKey、model（三个字符串，存 shared_preferences）；备份文件路径。
- **必要操作**：填/改/清 API key；导出备份；导入恢复（见第七节）。

### 5.5 课表模块（V1 仅占位）
- **必要数据**：无。
- **必要操作**：点击显示"V2 开放"提示，不崩溃。

## 六、各个模块的关系

**核心原则：数据层分三类独立管理，显示层混排。**

```
录入（手动 / AI）  ──写入──▶  数据层
                                 ├─ courses 表（周期规则，改一次=改整学期）
                                 ├─ events 表（绝对时刻，改一次=改这一次）
                                 └─ tasks 表（日期，打勾消失）
                                        │
                   ┌────────────────────┼────────────────────┐
                   ▼                    ▼                    ▼
              日程列表            课表网格              提醒调度
        课程展开成日期后混排     就地渲染周期块      读 events/tasks 时刻
```

**关键关系说明**：

1. **课程不能被当成"很多条待办"存**。它的更新语义是"改一次 = 改整学期"，改的是规则；待办改一次只影响那一条。塞进同一张表会导致更新逻辑互相污染。
2. **混排只在显示层做**：课程按周期规则展开成具体日期 → 与事件、任务按时间排序。课表网格则是"就地渲染"，不展开。
3. **提醒模块只读时间和标题**，不关心条目来自哪张表；事件和任务的提醒策略不同（事件到点提，任务当天提一次），差异在调度时决定。
4. **设置模块是横向依赖**：AI 对话要读它的 key；备份恢复要读它的文件配置。它不存任何业务条目。

## 七、本地数据文件、备份和恢复要求

### 7.1 数据文件位置与形态

| 内容 | 存储 | 位置（Android 应用私有目录） |
|---|---|---|
| 三张业务表 | sqflite 2.4.6 | `/data/data/<包名>/databases/todo.db` |
| API key / baseURL / model / 偏好 | shared_preferences 2.5.6 | `/data/data/<包名>/shared_prefs/` |

- 应用私有目录**用户无法直接访问**，卸载 App 会一并删除——这就是必须提供备份/恢复的原因。
- API key **绝不进业务表**，单独存、单独清。

### 7.2 备份要求

- **触发方式**：用户在「我的」页手动点"导出备份"，不自动、不联网、不云同步。
- **产物**：一个带版本号的 JSON 文件（如 `todo-backup-v1-20261121.json`），包含三张表的全部数据；导出到用户可访问目录（Download 或系统文件选择器）。
- **API key 处理（2026-11-21 用户拍板，定稿）**：**默认不含 key**。理由：备份文件是最易外泄的一种文件（Download / 微信 / 网盘），而 key 泄露会导致 DeepSeek 额度被盗刷（真金白银）；换机重填 key 只需约 1 分钟，收益远小于风险。如需连配置一起备份，另设**高级选项「包含配置」**（默认关，用户主动勾选才生效，勾时明确警示"文件含明文 key，勿外传"）。
- **格式自描述**：文件头带 schema 版本号，恢复时校验，版本不兼容要给出明确提示而不是崩溃。

### 7.3 恢复要求

- **触发方式**：用户手动点"导入恢复"，选 JSON 文件。
- **行为（2026-11-21 用户拍板，定稿）**：**覆盖式恢复**——导入前二次确认"将覆盖当前所有数据"，确认后清空三张表再写入。理由：备份的真实场景是换机/重装/卸载前，导入时手机要么是空的要么是要丢弃的数据；"两份数据要合并"在自用无云同步的 App 里几乎不存在，不值得为它承担合并去重与冲突规则的复杂度。
- **失败处理**：文件损坏 / 版本不兼容 / 中途失败 → 保留原数据不动，给出明确错误提示。
- **不做**：自动合并、增量恢复、跨版本迁移（V1 不做，超出范围）。

### 7.4 与分发的关系

发 APK 给朋友是"各用各的"——朋友拿到的是空数据。备份/恢复是**用户自己换机、重装、卸载前**的保护手段，不是分享数据的通道。

## 附录 B：技术决策备忘

1. **相对时间**：AI 请求必须注入"今天是 YYYY-MM-DD 星期X"，否则"周五17点""12.03""下周三"全算错。
2. **结构化输出**：让模型返回 JSON（JSON mode / function calling），App 直接渲染，不用自由文本 + 正则。
3. **API key**：不写死、不进 git；客户端存 key 有反编译风险 → 设额度上限、用便宜模型。
4. **插件选型**：通知用 `flutter_local_notifications` 23.0.3（2026-11-18 发布，活跃），**不用** `awesome_notifications`（0.12.1，仍 0.x）。V0 加 `timezone`（`zonedSchedule` 需要），删掉模板残留的 `material_ui`。
5. **开源借鉴**：`justsandip/flutter-local-notifications-example`（22★）的单例服务类、`tz.initializeTimeZones()` 初始化顺序、`zonedSchedule` 的 `absoluteTime` + `androidAllowWhileIdle: true` 参数组合可抄；但它只请求 iOS 权限，Android 13+ 的 `POST_NOTIFICATIONS` 必须自己写。`theakhinabraham/doable-todo-list-app`（111★）的分层可参考 V1，但其 `rescheduleAllNotifications` 有条件写反的 bug，勿抄业务逻辑。
6. **GitHub 访问**：本机直连不通，但 WebFetch 服务端通道可读 GitHub API——搜源码/读源码走 WebFetch，整仓下载需 Gitee 中转。

### E.2 OriginOS 后台保活三件套（V2 前置手动配置）

以下路径来自 **vivo 官方社区技术支持回复**（2024-06-19），是让定时提醒在 OriginOS 上不被冻结的必要用户配置：

1. **开自启动**：设置 → 顶部搜索「自启动」→ 开启本 App 的自启动开关。
2. **锁后台**：屏幕底部上滑进入近期任务 → 找到本 App 卡片 → 按住卡片**下滑加锁**（加入一键加速白名单）。
3. **允许后台高耗电**：设置 → 顶部搜索「后台耗电管理」→ 找到本 App → 允许后台高耗电。

另需注意：OriginOS 4+ 若开启「睡眠模式」或「超级省电模式」，夜间会间歇性冻结后台消息、甚至熄屏 5 分钟断网——**V2 的白名单指引要提醒用户关掉这两项**，否则夜间提醒会丢。

### E.3 V0 真机排查结论（2026-11-21，务必保留）

1. **FLN 16+ 必须在 App 自己的 Manifest 声明 `ScheduledNotificationReceiver`**（以及开机重注册用的 `ScheduledNotificationBootReceiver`）。漏掉时 alarm 正常触发、权限全部正常、channel 正常，但通知**永远不弹**，且没有任何 error 日志。验证命令：`adb shell dumpsys package com.anlu.todo_app | grep ScheduledNotificationReceiver` 必须有输出。
2. **channel 必须显式创建**：仅靠 `AndroidNotificationDetails` 里的 channel 参数不够，真机上会出现 channel 不存在、通知被静默丢弃。在 `init()` 里显式 `createNotificationChannel()` 后修复。
3. **时区不是本次故障原因**：`tz.local` 未设置时是 UTC，但 `TZDateTime.from(DateTime.now(), UTC)` 保留的是**同一时刻**（本地 18:02 → 存成 10:02 UTC），插件再按 `timeZoneName` 还原，调度时间正确。排查时读 `run-as com.anlu.todo_app cat /data/data/com.anlu.todo_app/shared_prefs/scheduled_notifications.xml` 核对 `scheduledDateTime` 与 `timeZoneName`，别凭猜。
4. **二分诊断法**：加「立即弹通知」按钮。即时能弹说明通知投递/权限/渠道都正常，问题只在调度接收链路；本次正是靠这一步把范围缩到 receiver。
5. **任务记录会被清理**：receiver 成功发通知后会调用 `removeNotificationFromCache`；若 prefs 里的 `scheduled_notifications` 长期残留同一条，说明 receiver 没跑完。

### E.4 分发给朋友的机型风险

APK 发朋友后各人机型不同（见第三节分层图）。V2 完成硬提醒后：
- 在「我的」页放一份**机型适配指引**，至少覆盖 OriginOS（iQOO/vivo）、MIUI、EMUI 三大 ROM 的白名单路径；
- 或引入 `device_info_plus` 检测 ROM 类型，弹出对应品牌的设置引导（V2 实现时再定）。
- **不承诺所有机型都准时响**——国产 ROM 冻结策略差异是系统级限制，不是 App 能单方面绕过的。

## 附录 F：AI 提示词定稿（2026-11-21 用户拍板）

### F.1 三条必须先定的产品决策

用户在 2026-11-21 明确拍板，后续不许再改口径，除非重新讨论：

1. **支持一句话多件事**：AI 返回 `items` 数组，一句里说两件（"周五考试，周日交作业"）就出两条草稿，逐条确认。**不采用"只取第一件"**——会静默丢数据。
2. **已过的时间算下一次**：今天是周六说"周五17点"→ 下周五（11-27），不是昨天（11-20）。理由：过去的日期排不了提醒，只会卡在报错上。
3. **只说日期没给钟点的任务，当天 09:00 提醒**：不是"不提醒"。09:00 比 08:00 更贴合大一早课作息。

### F.2 提示词必须写死的规则（缺一条就会真实出错）

| 规则 | 不写会怎么错 |
|---|---|
| 「周五」「周三」取**下一次出现**；本周那天已过就算下一周 | 返回过去的日期 |
| 「下周三」= 下一个自然周的周三，不是 7 天后 | 差整整一周 |
| 「12.03」「12/3」按 **月.日** 理解；今年已过算明年 | 被理解成 3 月 12 日 |
| 「明天」「后天」按今天递推 | — |
| 只给日期没给钟点 → `time` 填 `null`，不许编造 | 模型爱凭空造 09:00 |
| `title` 保留原词，去掉时间地点，不加「参加/去/完成」，不翻译 | 标题变成「参加E栋104的考试」 |
| `location` 照抄原文，`note` 放额外要求 | 地点混进标题 |
| 不确定的字段一律 `null`，不许猜 | 编造地点 |

### F.3 输出格式与三个坑

1. **用 `{"items":[...]}` 包裹，不用裸数组**：OpenAI 兼容的 `json_object` 模式要求顶层是对象，裸数组会被服务端拒绝。
2. **解析层要兼容三种形态**：`{"items":[...]}`、裸数组、单个对象。模型不总是听话，兼容成本很低。
3. **缺 `title` 的条目跳过，不抛整体异常**：一条脏数据不该拖垮整批草稿。

### F.4 prompt 必须注入的变量

- `{TODAY}`：`yyyy-MM-dd`
- `{WEEKDAY}`：星期几（中文）
- `{HHMM}`：当前时刻。**只有日期不够**——"17点"在 21:19 这一刻已经过了，模型需要知道现在几点才能判断。

### F.5 定稿文本位置

唯一真相源：`app/lib/services/ai_service.dart` 的 `AiService.systemPrompt`。
改提示词必须同步 `app/test/ai_service_test.dart` 里「提示词含三条定稿规则」这条测试，否则测试会红——这是故意的，防止悄悄改口径。
